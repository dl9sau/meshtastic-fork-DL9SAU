Changelog — DL9SAU fork of meshtastic/firmware
==============================================

Local divergences from upstream master. Entries newest first.


2026-05-25  Stage 2 v2 — role-aware own-TX + relay direct-source rule
---------------------------------------------------------------------
Three related refinements to Stage 2 driven by a second pass on the
"who should be defensive when" question.

A) Own TX is now differentiated by role. Stage 2 own-TX modulation
   only applies to CLIENT and CLIENT_BASE — every other role goes
   vanilla, because those roles exist for a specific publishing
   purpose (SENSOR exists to publish sensor data, TRACKER exists to
   publish positions, ...) and throttling them would defeat their
   stated intent.

   * CLIENT (generic mobile user node) — defensive:
       Position  : hop=min(conf,2), CR=5,        pwr=default
       Telemetry : hop=0,           CR=5,        pwr=conf-6 (≥10)

   * CLIENT_BASE (stationary infrastructure node) — full visibility:
       Position  : hop=default,     CR=default,  pwr=default
       Telemetry : hop=0,           CR=default,  pwr=default
       (telemetry hop=0 stays because it is heartbeat data — even
        a base station gains nothing by propagating it further.
        If a future use-case needs gateway/MQTT reach we can
        revisit and bump it to 1 or 2.)

   * SENSOR / TRACKER / TAK_TRACKER / LOST_AND_FOUND /
     CLIENT_MUTE / CLIENT_HIDDEN / REPEATER / ROUTER /
     ROUTER_LATE: untouched, fully vanilla. CLIENT_HIDDEN is
     already heavily restricted by Stock (auto rebroadcast_mode =
     LOCAL_ONLY, NodeInfo and telemetry suppressed) — nothing
     for us to add.

B) Relay path gains a "direct-source" exception in
   FloodingRouter::applyClientRepeatPolicy.

   If getHopsAway(*tosend) == 0 (i.e. the packet still carries its
   original hop_limit, meaning we are the first relay in the chain
   and the originator was a direct neighbour), the packet is now
   forwarded with the configured CR and full configured power, no
   override. Rationale: when nobody else has retransmitted it yet,
   our relay is the only one putting it on the air for the next
   hop — it needs full punch to actually reach that next hop.

   Once a packet has been seen via at least one intermediate relay
   (hopsFromOriginator > 0), it has been amplified by the mesh
   already, and our additional relay can safely run reduced.

   getHopsAway == -1 (unknown, e.g. old firmware origin or
   encrypted packet without a reliable hop_start) falls through to
   the B2 default reduction — safe-by-default.

C) CLIENT_BASE relay caps further propagation.

   In the B2 reduced-relay branch (= we are relaying an already-
   seen packet at lower power / CR=5), CLIENT_BASE additionally
   sets tosend->hop_limit = 0. Effect: our direct neighbours
   still hear our relay, but they won't forward it.

   Rationale: a base station typically sits among other infra —
   once it has done its courtesy relay, propagating further is
   redundant and burns shared airtime. CLIENT (mobile) keeps the
   standard hop budget because it may sit at a bridge position.

Footprint:
   src/modules/PositionModule.cpp                  (role gate)
   src/modules/Telemetry/{Device,Environment,Health,
                          AirQuality,Power}Telemetry.cpp (role gate)
   src/mesh/FloodingRouter.cpp                     (B3 ext + B2 hop)

Updated observable-behaviour table:

  +---------------------------+------------------------+------------------------+----------+
  | Action                    | CLIENT                 | CLIENT_BASE            | other    |
  +---------------------------+------------------------+------------------------+----------+
  | Send own Position         | hop≤2, CR=5,           | hop=default,           | vanilla  |
  |                           |   pwr=default          |   CR/pwr=default       |          |
  | Send own Telemetry        | hop=0, CR=5,           | hop=0,                 | vanilla  |
  |                           |   pwr=conf-6 (≥10)     |   CR/pwr=default       |          |
  +---------------------------+------------------------+------------------------+----------+
  | Relay drop:               | telemetry, undecodable, non-core portnums           | vanilla  |
  | Relay full pwr+CR:        | TRACEROUTE, ROUTING, direct-DM to 12 h-known        | vanilla  |
  |                           |   neighbour (next_hop=us), packet direct from       |          |
  |                           |   originator (getHopsAway==0)                       |          |
  | Relay reduced (B2):       | CR=5, pwr=conf-6       | CR=5, pwr=conf-6       | vanilla  |
  |                           |   (≥10)                |   (≥10), hop_limit=0   |          |
  +---------------------------+------------------------+------------------------+----------+

  "other" = SENSOR / TRACKER / TAK_TRACKER / LOST_AND_FOUND /
  CLIENT_MUTE / CLIENT_HIDDEN / REPEATER / ROUTER / ROUTER_LATE.

Why this is coherent:
  - CLIENT rule       = "always CR=5, sometimes reduce pwr/hop".
  - CLIENT_BASE rule  = "always default CR/pwr, sometimes reduce hop".
  - Everyone else     = no change. The user picked that role for a
                        reason; respect their intent.


2026-05-24  Fix Stage 3 user-override on nRF52 + tx-power resolver
------------------------------------------------------------------
Field test showed the Stage 3 user-override magic word was NOT
surviving the firmware-driven soft reboot on nRF52 (T1000-E).
Reproduction: manually switch from LongFast to MediumFast → reboot
(intentional, LoRa-config change) → ~20 min later the device
silently rebooted again and switched back to LongFast. That's
exactly the failure mode the magic word was supposed to prevent.

Root cause:
  Our magic lived in plain `.noinit` RAM
  (__attribute__((section(".noinit")))). On nRF52 with SoftDevice
  the Adafruit bootloader / C runtime appears to zero that RAM at
  boot, so the magic was lost. `.noinit` is not hardware-retention,
  it's just "C runtime won't touch this". If anything else does
  (bootloader, SD), the contract is broken.

Fix — platform-specific hardware-retention registers:
  * nRF52 (T1000-E): use NRF_POWER->GPREGRET2 (8-bit register).
    GPREGRET is already used in upstream code for
    NRF52_MAGIC_LFS_IS_CORRUPT and DFU_MAGIC_SKIP; GPREGRET2 is
    free. Both are hardware-guaranteed to retain across
    NVIC_SystemReset and hardware-guaranteed to clear on power-on
    / pin reset. Perfect semantics, zero CRT involvement.
  * ESP32 (Heltec Wireless Tracker etc.): RTC_NOINIT_ATTR places
    the variable in RTC slow memory, which on Espressif silicon
    is the same kind of "retained across reset, cleared on
    power-on" memory. Kept as-is — the bug was nRF52-specific.
  * Other platforms: still .noinit best-effort. Portduino has no
    real need for this.

Magic value shrunk from 32-bit to 8-bit because GPREGRET2 is 8-bit
wide. AUTO_OVERRIDE_MAGIC = 0xA5.

Additionally added a one-time boot log so the user can confirm
the magic survived: GeoPresetSwitcher logs the initial magic
value the first time evaluate() is called after boot.

Lesson kept here for future reference: when you want "retained
across soft reset, cleared on power cycle" RAM on a platform
that has SoftDevices / bootloaders touching memory at boot,
.noinit alone is NOT enough. Use the platform's hardware
retention register / RTC slow memory. The two natural pairs are:
  - nRF52: NRF_POWER->GPREGRET / GPREGRET2
  - ESP32: RTC_NOINIT_ATTR

Second lesson (the one we walked into after the first fix):
on nRF52 with an *active* SoftDevice, direct writes to the
NRF_POWER->GPREGRET / GPREGRET2 registers are masked by the
SoftDevice. The CPU writes go through but the register state
isn't preserved across the soft reset the way you'd expect.
You MUST go through the SoftDevice SVC calls:

    sd_power_gpregret_clr(id, 0xFF);
    sd_power_gpregret_set(id, magic);
    sd_power_gpregret_get(id, &out);

where id = 0 → GPREGRET, id = 1 → GPREGRET2. Upstream main-
nrf52.cpp uses exactly this pattern for the LFS-corrupt and
DFU-skip magics. We mirror it for the auto-switch override
magic, and only fall back to the direct register access if
the SoftDevice call returns != NRF_SUCCESS (which happens
e.g. when the SoftDevice isn't initialised yet — early boot).

So the full rule for "retained across soft reset, cleared on
power cycle" on nRF52 + SoftDevice is:
  - Use GPREGRET / GPREGRET2 (hardware-retained register).
  - Access them via sd_power_gpregret_* (SoftDevice gateway).
  - Fall back to direct NRF_POWER->... only when the SVC call
    fails.

Translated:
  "hardware-guaranteed" was right about the silicon, but
  understated the software stack on top of it. The combination
  hardware register + SoftDevice gateway is what's actually
  reliable.


2026-05-24  Stage 2 — effectiveConfiguredTxPower() helper
---------------------------------------------------------
Stage 2's "configured TX power − 6 dB, floor 10 dBm" derivation
previously read config.lora.tx_power literally. When the user
leaves that at 0 ("use region default"), upstream
RadioInterface::applyModemConfig resolves it to myRegion->
powerLimit (and a final fallback of 17 dBm), so the device
actually transmits at e.g. 22 dBm — but our Stage 2 code derived
0 - 6 = -6 → floor 10 dBm. Telemetry and client relays therefore
went out at 10 dBm even when the device was effectively running
22 dBm, which is far weaker than intended.

Fix — new inline helper effectiveConfiguredTxPower() in
MeshRadio.h that mirrors the upstream resolution. A second inline
reducedTxPowerForStage2() composes it with the -6 dB / floor 10
formula. Both callers updated:
  src/modules/Telemetry/{Device,Environment,Health,AirQuality,
                         Power}Telemetry.cpp
  src/mesh/FloodingRouter.cpp


2026-05-24  Stage 2 activation — per-packet CR / power overrides live
---------------------------------------------------------------------
The Stage 2 plumbing committed earlier is now driven from the actual
sender / relay sites. Verified field-build clean.

A) Own outgoing traffic:
   * PositionModule::sendOurPosition stamps tx_cr_override=5 (no
     power override — position must remain reachable).
   * DeviceTelemetry, EnvironmentTelemetry, HealthTelemetry,
     AirQualityTelemetry, PowerTelemetry stamp:
       tx_cr_override = 5
       tx_power_override = max(config.lora.tx_power - 6, 10)
     (in addition to the existing hop_limit=0 from Stage 1).

B) Relay path — FloodingRouter::applyClientRepeatPolicy:
   * Helper called from NextHopRouter::perhapsRebroadcast right
     before send. Decision tree:

       Role != CLIENT && role != CLIENT_BASE
         → return true, no change (vanilla relay behaviour
           preserved for REPEATER / ROUTER / ROUTER_LATE / etc.)

       B1 drop (return false → packet pool release, no TX):
         • which_payload_variant != decoded_tag (undecodable)
         • portnum == TELEMETRY_APP
         • portnum not in core repeat-whitelist:
             TEXT_MESSAGE_APP, TEXT_MESSAGE_COMPRESSED_APP,
             POSITION_APP, NODEINFO_APP, ROUTING_APP, ADMIN_APP,
             ALERT_APP, KEY_VERIFICATION_APP, WAYPOINT_APP,
             STORE_FORWARD_APP, TRACEROUTE_APP,
             STORE_FORWARD_PLUSPLUS_APP.

       B3 exception (return true, no override):
         • portnum == TRACEROUTE_APP
         • portnum == ROUTING_APP
         • direct-DM where next_hop == us AND p->to has
           has_hops_away && hops_away == 0 && last_heard within
           the last 12 h.

       B2 default (return true with overrides):
         tx_cr_override = 5
         tx_power_override = max(config.lora.tx_power - 6, 10)

Implementation footprint:
   src/modules/PositionModule.cpp
   src/modules/Telemetry/{Device,Environment,Health,
                          AirQuality,Power}Telemetry.cpp
   src/mesh/FloodingRouter.{h,cpp}   (new helper)
   src/mesh/NextHopRouter.cpp        (calls the helper)

2026-05-24  Stage 2 plumbing — per-packet CR / TX-power override fields
-----------------------------------------------------------------------
Lays the infrastructure for Stage 2 / 4 without enabling any new
behaviour yet — dormant code, builds clean, no sender sets the
override flags so RX/TX behaviour is bit-for-bit identical.

What landed:
* meshtastic_MeshPacket gained three transient fields with nanopb-
  style has_* flags (NOT serialised; the wire encoding walks the
  X-Macro _FIELDLIST only, not the struct):
    has_tx_cr_override     / tx_cr_override      (uint8_t)
    has_tx_power_override  / tx_power_override   (int8_t)
    has_tx_preset_override / tx_preset_override  (uint8_t, Stage 4)
  packetPool.allocZeroed() naturally starts every packet with "no
  override" because all has_* default to false.
* RadioInterface base class got two new virtuals:
    int16_t setRuntimeCodingRate(uint8_t cr)
    int16_t setRuntimeTxPower(int8_t dBm)
  Default implementation returns -1 ("not supported"). The four
  real RadioLib backends (RF95Interface, SX126xInterface,
  SX128xInterface, LR11x0Interface) override both with thin
  wrappers around the RadioLib setCodingRate / setOutputPower
  calls. SimRadio inherits the no-op default.
* RadioLibInterface::startSend honours the override flags:
  - save the current cr / power members
  - call setRuntime* with the override value
  - if the backend returns -1, mark the override as not-applied
  RadioLibInterface::completeSending restores cr / power via
  setRuntime* after every TX, conditional on the save-state.
  Two new protected members in RadioLibInterface track the
  save-state: txCrOverrideActive / txCrOverrideSaved,
  txPowerOverrideActive / txPowerOverrideSaved.

What deliberately did NOT land:
* No sender site sets the override flags yet — PositionModule,
  the telemetry modules, FloodingRouter / NextHopRouter
  perhapsRebroadcast are unchanged. That's the next step
  (planned next) and will activate Stage 2's policy.
* No Stage 4 preset-override honouring in startSend yet — the
  has_tx_preset_override field exists but is not consulted.
  Adding that needs the full reconfigure() dance, which we'll
  build with Stage 4.


2026-05-24  Stage 3 refinement: outside-all-regions fallback = LongFast
-----------------------------------------------------------------------
Originally GeoPresetSwitcher only fired a switch when the local
position landed inside one of the hardcoded bounding boxes; outside
all boxes it did nothing. Field testing showed the natural mental
model is "drive into Berlin → MediumFast, drive out → LongFast".

GeoPresetSwitcher::evaluate() now treats any position outside all
known regions as "target = LongFast" and switches accordingly. The
user-override magic still applies: anyone who *manually* picks
e.g. MediumFast outside a region will stay there until power-cycle,
even though Auto would otherwise force LongFast. We deliberately
keep the override in noinit RAM (= cleared by power cycle) instead
of persisting it to flash; a persistent override would require
explicit reset via admin action or backup-restore, which the user
finds too cumbersome.


2026-05-24  Force CR=8 over CR=5
--------------------------------
DL9SAU prefers the more redundant 4/8 coding rate even on fast modem
presets. AdminModule's LoRa-config handler now rewrites coding_rate
from 5 to 8 whenever it would otherwise stick at 5. CR=6 and CR=7
entered by the user are honoured as-is. CR=8 is unchanged (the long-
range presets — LongSlow, LongModerate, LongTurbo — already default
to it).

Implementation detail: RadioInterface::applyModemConfig honours a
custom coding_rate in [LORA_CR_MIN..LORA_CR_MAX] even when
use_preset=true, so the rule works uniformly for both preset and
custom configurations.

Side change to modemPresetForParams() in MeshRadio.h: CR is no
longer part of the reverse-lookup key — only BW and SF. Without
this, the new CR=5→8 rewrite would break the "rename primary
channel after custom config matches a preset" feature from round 2.
No two presets in the table share the same (BW, SF) but differ in
CR, so dropping CR from the match is loss-free.


2026-05-24  iOS app round 2 — BW picker + channel rename on custom mode
-----------------------------------------------------------------------
Two more iOS-specific quirks reported while testing the Stage-1 fixes:

* Bug 1: with our config.lora bandwidth mirror in place (Stage 1),
  the iOS LoRa screen displays "31 kHz" instead of the actual 250 kHz.
  Root cause is in Meshtastic-Apple LoRaConfig.swift / Bandwidths
  enum: the picker tags the 250 kHz row with proto value 0
  (`tag(bw.rawValue == 250 ? 0 : bw.rawValue)`), all others 1:1.
  When the firmware mirrors the real 250, iOS can't find a tag and
  falls back to the first row (31). See meshtastic/Meshtastic-Apple
  issue #1192.

  Fix: after mirroring, if the resulting bandwidth code is exactly
  250 we rewrite it to 0. The radio ignores config.lora.bandwidth
  while use_preset=true (RadioInterface::applyModemConfig honours
  the preset's BW), so this is purely cosmetic plumbing for iOS.

* Bug 2: setting SF=9 / BW=250 manually in the iOS app (i.e.
  use_preset=false) does not flip the primary channel name to
  "MediumFast", even though SF=9/BW=250/CR=5 is functionally
  MediumFast. Our Stage-1 auto-rename gated on
  oldConfig.modem_preset != new && use_preset.

  Fix: switch the auto-rename trigger to an *effective* preset
  comparison. New helper modemPresetForParams(bw, sf, cr,
  wideLora) in MeshRadio.h reverse-looks-up the preset that
  matches a given parameter triple (or returns MODEM_PRESET_END).
  AdminModule now compares oldEffective vs newEffective: if
  use_preset=true the value comes from modem_preset, otherwise
  from the reverse lookup. If they differ AND the new effective
  preset is known, we rename the primary channel — and also
  engage the geo auto-switcher's user-override magic, same as
  before.

  Side effect: setting bizarre custom values that don't match any
  preset (e.g. SF=10/BW=125/CR=8) leaves the channel name
  untouched (newEffective == MODEM_PRESET_END), which is the
  correct behaviour.


2026-05-24  Stage 3: geo-fenced auto modem-preset switch
--------------------------------------------------------
Switches config.lora.modem_preset automatically based on the
current GPS position, so a traveller does not have to fiddle
with settings when crossing into Berlin, Stuttgart/Tübingen
etc. No internet / no proto changes — purely on-device.

New files:
* src/mesh/GeoPresetSwitcher.{h,cpp} — owns the region table,
  the cadence/cooldown throttles, the user-override bookkeeping,
  and the actual switch (writes config.lora, calls Channels::
  renamePrimaryForPresetChange, persists, requests reboot).

Refactor:
* Channels::renamePrimaryForPresetChange() extracted from the
  AdminModule lora-tag handler so both the user-initiated path
  and the auto-switch share the same naming convention.
* AdminModule::handleSetConfig: detects a user-initiated
  modem_preset change (= one that did not originate from the
  auto-switcher, checked via geoPresetSwitcher.
  isAutoSwitchInProgress()) and parks a magic word in noinit
  RAM via GeoPresetSwitcher::markUserOverride(). The auto-
  switcher honours that magic and stays out of the way.

Hook:
* PositionModule::runOnce calls geoPresetSwitcher.evaluate()
  every tick (5 s default); internal 20-min throttle filters.

Region table (hardcoded, EU868 only):
* Berlin (city proper, Brandenburg deliberately out)
  52.35°–52.70° N × 13.10°–13.70° E  → MediumFast
* Stuttgart / Reutlingen / Tübingen corridor
  48.25°–48.80° N × 8.90°–9.35° E    → MediumFast
* Rheinland (Cologne / Bonn)
  50.50°–51.20° N × 6.50°–7.50° E    → ShortSlow

Tuning:
* Re-evaluation cadence: 20 min.
* Cooldown after a switch: 20 min.
* Inward boundary margin: ~5 km (450 000 / 750 000 in 1e-7°
  for lat/lon, fixed for mid-latitudes Europe).

Activation gate:
* config.lora.region == EU_868
* config.lora.use_preset == true   (users on custom SF/BW are
  intentionally exempt — that's their "off switch")
* No user-override magic in noinit RAM

User-override mechanics:
* AUTO_OVERRIDE_MAGIC is written into a noinit RAM cell
  (RTC_NOINIT_ATTR on ESP32, __attribute__((section(".noinit")))
  elsewhere). That cell survives a soft reboot — including our
  own preset-change-triggered reboot — but is undefined after a
  power cycle or hardware reset, so the magic no longer matches
  and the auto-switcher resumes. This matches the user request:
  "wenn ich wieder in den auto mode gehen moechte mache ich
  einen Neustart."


2026-05-24  Hop-limit overrides for own position/telemetry
----------------------------------------------------------
* DeviceTelemetry, EnvironmentTelemetry, HealthTelemetry,
  AirQualityTelemetry, PowerTelemetry:
  set p->hop_limit = 0 before sendToMesh, so direct neighbours
  do not rebroadcast our telemetry. Telemetry is per-node noise;
  neighbours seeing it once is enough.

  at min(configured, 2). Position is high-volume on a busy mesh
  and 2 hops is plenty for "where am I" updates.

TODO — Stage 2: per-packet CR + TX-power overrides
--------------------------------------------------
Stage 2 is one cohesive change because all of the following pieces
share the same per-packet override plumbing in the radio path.

A) Own traffic (originating from us):
   * Own telemetry sent with CR=5 and TX-power = configured - 6 dB,
     but at least 10 dBm, regardless of global LoRa config.
   * Own position sent with CR=5 and configured TX-power (unchanged),
     regardless of global LoRa config.

B) Repeat traffic (we relay someone else's packet) — only relevant
   for roles CLIENT and CLIENT_BASE (the two roles that actively
   repeat as "user" nodes; REPEATER / ROUTER / ROUTER_LATE etc. are
   intentionally unchanged):

   B1) Drop-filter — we refuse to repeat at all. The repeat
       whitelist is the upstream CORE_PORTNUMS_ONLY core list
       MINUS telemetry. Everything else is dropped:

       Repeat whitelist (these portnums pass the filter):
         * TEXT_MESSAGE_APP
         * TEXT_MESSAGE_COMPRESSED_APP
         * POSITION_APP
         * NODEINFO_APP
         * ROUTING_APP
         * ADMIN_APP
         * ALERT_APP
         * KEY_VERIFICATION_APP
         * WAYPOINT_APP
         * STORE_FORWARD_APP
         * TRACEROUTE_APP
         * STORE_FORWARD_PLUSPLUS_APP

       Drop unconditionally:
         * TELEMETRY_APP (explicitly removed from the whitelist —
           per-node telemetry has no value when relayed by a
           client; the upstream node will just receive the data
           once from its own neighbour layer).
         * Anything else (non-core portnums: NEIGHBOR_INFO,
           RANGE_TEST, ATAK_PLUGIN/FORWARDER, PAXCOUNTER, SERIAL,
           IP_TUNNEL, AUDIO, DETECTION_SENSOR, etc.). Same
           rationale: as a client tracker we don't propagate
           experimental / niche-app traffic for others.
         * Packets we couldn't decode (which_payload_variant !=
           decoded_tag after perhapsDecode), i.e. foreign-channel
           / wrong-PSK traffic and packets that survived decode
           without success.

       This matches upstream's CORE_PORTNUMS_ONLY filter in
       intent but is stricter (drops telemetry) and is applied
       unconditionally for roles CLIENT / CLIENT_BASE, not via
       rebroadcast_mode config. Users who want NEIGHBOR_INFO or
       experimental modules propagated can run a REPEATER /
       ROUTER role.

   B2) Default repeat power/CR — for everything that does pass the
       filter:
       * CR = 5 regardless of global LoRa config.
       * TX-power = configured - 6 dB, floor 10 dBm.

   B3) Exceptions — repeat at full configured power and configured
       CR (i.e. no override), because these must stay debuggable:
       * Direct-message we are the next_hop for (p->next_hop ==
         lastByte(getNodeNum()) AND the destination p->to is a node
         in our NodeDB with has_hops_away && hops_away == 0 AND
         last_heard within the last 12 h. The "12 h direct-heard"
         test uses the existing NodeInfoLite fields, no new state.
       * TRACEROUTE_APP packets (the user's "ping" in everyday
         usage — Meshtastic's ping button issues a traceroute).
       * ROUTING_APP packets (ACK/NAK and routing control traffic).
         These must remain as reliable as configured so that the
         user can diagnose *why* a message did or did not arrive.

Note on ROUTING_APP and next-hop learning:
NextHopRouter::sniffReceived only updates origTx->next_hop in
response to ACK/reply packets (those with request_id or reply_id
set). So forwarding ROUTING_APP at full power does make us
slightly more attractive as a next_hop. We accept that trade-off
because reliable ACKs matter more for end-user experience than
shaving a bit off our next_hop attractiveness in a client role.
If this becomes a problem we revisit B3.

Why CR=5 works even when the mesh runs CR=8:
LoRa explicit-header mode (which Meshtastic uses) carries the
payload CR in the header. The header itself is always sent at the
most-redundant CR=4/8. Receivers configured for any CR can therefore
decode any payload CR, as long as SF and BW match.

Implementation sketch:
1. Add transient (non-proto) override fields to MeshPacket, e.g.
   tx_cr_override and tx_power_override (signed int8, 0 = "no
   override"). These never go over the air; they live only on the
   local TX queue.
2. In RadioLibInterface::startSend(), before configHardwareForSend(),
   check the override fields and:
     - if cr_override is set and differs from current cr, call
       iface-specific setCodingRate() and remember the previous cr;
     - same for tx_power_override / setOutputPower().
3. After startTransmit returns (TX done), restore the previous cr
   and power, so subsequent packets and RX use the configured ones.
4. Touch all radio backends:
     - RadioLibRF95 / RF95Interface
     - SX126xInterface
     - SX128xInterface
     - LR11x0Interface
     - SimRadio (portduino)
5. Apply overrides at packet-creation sites:
   * PositionModule::sendOurPosition (set CR override only).
   * DeviceTelemetry / Environment / Health / AirQuality / Power
     (set CR override + power override).
   * NextHopRouter::perhapsRebroadcast and FloodingRouter::
     perhapsRebroadcast for the relay path, with the B1/B2/B3
     decisions above.

Caveats / open questions:
* Reconfigure latency vs. carrier-sense window — measure on T1000-E.
* TX-power floor of 10 dBm vs. region power cap (EU868 = 14 dBm);
  -6 dB hits 8 dBm and gets clamped up to 10 dBm. Fine on T1000-E.
* CR override is a no-op when global CR is already 5 (LongFast,
  Medium*, Short*) — skip the reconfigure cost in that case.
* The "next_hop == us" condition for the direct-DM exception needs
  to use the canonical lastByte(getNodeNum()) trick already used in
  NextHopRouter::perhapsRebroadcast (line ~132).
* Decide whether to expose this behaviour via userprefs or hardcode.

TODO — Stage 4: dual-preset position beacon for lost-device recovery
--------------------------------------------------------------------
Goal:
For roles ≤ CLIENT (i.e. CLIENT, CLIENT_BASE, CLIENT_MUTE, SENSOR,
TRACKER, TAK_TRACKER), if the device is currently running a non-
LongFast modem preset (any preset where SF or BW differ from
LongFast — CR is irrelevant), emit an *occasional* additional
position beacon on LongFast.

Rationale: if you lose the device while travelling on MediumFast,
a LongFast beacon increases the chance that *any* random
Meshtastic node within range — they typically default to LongFast
— can hear it and forward your position to your phone via MQTT /
the public network. This is a "sign of life on the mainland
preset", not a real-time position track.

Cadence (refined 2026-05-24):
The LongFast beacon is opportunistic, hooked onto the normal
position-broadcast path. Each time we are about to send a normal
position, check whether the last LongFast beacon went out more
than 1 hour ago. If yes, also emit the LongFast variant; if no,
skip it for this round. With the default position broadcast
interval, this naturally amortises to about one LongFast beacon
per hour while we are reporting, and stops entirely once we go
quiet. That keeps the "radio is blind to home-preset RX during
LongFast TX" window to ≤ 1 short burst per hour.

Implementation sketch:
1. Detect "non-LongFast" preset: SF != 11 || BW != 250 kHz when
   use_preset=true; same check via the explicit fields otherwise.
   See modemPresetToParams() in MeshRadio.h for the LongFast
   reference values.
2. PositionModule keeps a uint32_t lastLongFastBeaconMs. In the
   path that sends our position, if (millis() - lastLongFastBeaconMs
   > 3600000), also enqueue a duplicate position packet flagged
   for LongFast transmission, and update the timestamp.
3. Honor that flag in RadioLibInterface::startSend(): if the
   packet carries a "force-preset" override (the third per-packet
   override on top of Stage-2's CR + TX-power), call a full radio
   reconfigure() with the LongFast SF/BW/CR before startTransmit,
   then reconfigure() back to the home preset afterwards.
4. Backends touched: same as Stage 2 (RF95 / SX126x / SX128x /
   LR11x0 / SimRadio). The reconfigure path is more invasive
   than CR/power-only because BW and SF affect timing — but
   given the once-per-hour cadence this is acceptable.

Caveats:
* Reconfiguring BW/SF puts the radio out-of-mesh for the
  duration of the LongFast TX (~1–3 s for one Position packet)
  — RX of packets on the home preset is blind during that window.
  With ≤ 1 occurrence per hour this is a non-issue.
* The LongFast beacon should be sent on the default channel
  (empty-name → "LongFast" via the dynamic getName() fallback)
  with the default PSK so that *any* finder can decode it
  without sharing the home channel.
* Apply position_precision exactly as for the normal beacon —
  the LongFast variant must not leak a finer location than the
  user is already comfortable broadcasting on the home channel.
* Stage 4 logically depends on Stage 2 plumbing (per-packet
  radio override fields) — do Stage 2 first.
